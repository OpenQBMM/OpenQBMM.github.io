Validation · OpenQBMM 18

Running the tests and the validation

How the results on the validation page are produced, and how to reproduce them on your own build: the unit tests, the cases with their baselines and their reference data, and the tiers that run them together. Every command on this page is run from the top of the OpenQBMM sources, in a shell with the OpenFOAM environment loaded.

Requirements

  • OpenQBMM built, as in the installation guide
  • The whole tree: a sparse clone made for a build has to add test and validation
  • The unit tests built (below)
  • Python 3, with matplotlib for the figures and the report

01

What is checked

OpenQBMM is checked at three levels, which answer different questions.

Unit tests

The algorithms

Moment sets, moment inversion, advection schemes and sub-models, each tested on its own by a small program that compares what it computes with a known answer and exits with an error when they differ.

Baselines

The software

A case with a baseline is compared with its last accepted run: did a change move a result it was not meant to move? This says nothing about whether the result is right.

Reference data

The physics

A case with reference data is compared with experiments, analytical solutions or another method, within a tolerance set for each comparison by what agreement the model can be expected to reach.

02

Unit tests

./Allwmake does not build the unit tests. Build them, then run them all:

./test/Allwmake -j
./test/Allrun

The tests are OpenFOAM applications named Test-*, installed next to the solvers. test/Allrun runs every one of them, carries on past a failure, lists the tests that failed at the end and then exits with an error, so that a single run reports everything that is broken.

A test reads its dictionaries from the directory it is run in. To run one by itself, run it from the directory test/Allrun gives it, for example:

cd test/momentInversions/univariate/univariateMomentInversion
Test-UnivariateMomentInversion

A test with a testCase directory, such as populationBalanceSubModels or univariateQuadratureApproximation, is run from inside it. A few tests check that an invalid state stops the computation: they pass only when they stop with the expected message.

Convergence studies

test/univariateMomentAdvection holds the advection of the same distribution on a series of refined meshes, for the first-order and the zeta schemes. They measure the order of accuracy of the schemes, and each case has its own Allrun and Allclean. They are not part of test/Allrun; the ones that have a baseline are run by the tiers.

03

Running a case

Every case under tutorials/ and validation/ has an Allrun, which sets the case up from 0.orig, runs it and draws its figures, and an Allclean, which returns it to its initial state. A case is run in place:

cd validation/pbeFoam/<case>
./Allrun

Each step of an Allrun stops the case with an error when it fails, so that a broken case does not go on to draw graphs of an old result. For the same reason, a case that still holds a previous run fails at once with Run Allclean first: OpenFOAM does not run an application whose log file is already there, and the results compared would be those of the old run. To run a case again:

./Allclean
./Allrun

The Allrun of a case runs it; the checks against its baseline and its reference data are made by whatever runs the cases, or by hand:

bin/qbmmRegression check validation/pbeFoam/<case>
bin/qbmmCompareReference validation/pbeFoam/<case>

tutorials/Allrun and validation/Allrun run and check every case of their directory in place, the long ones and those meant to be run by hand included. To run a chosen set of cases, use the tiers.

04

Baselines

The baseline of a case, <case>/regression/baseline, is a summary of the fields of the last time the case writes, a few numbers per field: small enough to keep under version control and to read in a diff, and it moves when a field moves. A field is compared with its baseline to a tolerance relative to the span of the field, so that the tolerance means the same for a moment of order 10−12 and for one of order 106. The default is 10−8; a case sets its own in regression/tolerance.

# compare the last run of a case with its baseline
bin/qbmmRegression check <case>

# write the baseline of a case from its last run
bin/qbmmRegression record <case>

Recording a baseline is a decision taken case by case, never to make a failing check pass. A baseline is re-recorded when a change is meant to move the case, once the new result is understood and trusted, and in the same commit as the change, whose message says why the case moved.

05

Reference data

A case that is validated declares its figures and its comparisons in <case>/validation/validationDict, with the reference data under validationData. Each curve is declared once, in the figure it is drawn in; a curve the case computes names the reference curves it is held against and the tolerance of each, so that the graph and the number that judges it cannot come to disagree. The format is described in bin/python/qbmm/validation.py.

# how far the case is from its reference data
bin/qbmmCompareReference <case>

# draw its figures into <case>/validation/figures
bin/qbmmPlot <case>

The reference is interpolated onto the points of the case, over the interval the two share, and the difference is taken as a fraction of the scale of the reference: the larger of its span and its largest value. The tolerance applies to the root mean square of these fractions; the largest of them is reported beside it.

The figures need matplotlib; running and checking a case do not. Without it the figures are not drawn, which is said, and the case goes on. To use an interpreter of its own environment, name it with QBMM_PYTHON.

06

Tiers

bin/qbmmValidate runs a tier of the cases with the unit tests and reports how they came out: whether each case ran, how far it sits from its reference data, and whether it still matches its baseline. A case is any directory under tutorials/, validation/ or test/ with a baseline or a validationDict.

TierRunsTakesWhen
-quickEvery case that is neither long nor manualMinutesAfter any change to the sources
-baselinesEvery case with a baseline that is not manualA few hoursAt the end of a piece of work
-completeEvery case that is not manualA nightAt a milestone and before a release
manualThe cases no tier runs, which are run by handHours to daysWhen the model they test changes

The long and the manual cases are listed, with how long each takes, in validation/validationTiers. A new case that is short joins the quick tier by itself.

# the cases of a tier, without running them
bin/qbmmValidate -quick -list

# run a tier
bin/qbmmValidate -quick
bin/qbmmValidate -complete -j 8
OptionEffect
-listPrint the cases of the tier and run nothing
-j <cores>The cores to use, all of them by default; a case run in parallel counts for its number of subdomains
-dir <runDir>Where the cases are run, by default $FOAM_RUN/qbmmValidate/<tier>-<date>
-noTestsLeave out the unit tests
-output <dir>Write the report into <dir> rather than <runDir>/report; -style <css> gives it a stylesheet
-site <siteDir>Write the report into the validation page of a copy of this site (below)

The cases are copied into the run directory and run there, so that the sources stay clean and a run can be examined afterwards. Matplotlib is checked for before anything is run. The script exits with an error when a case or a unit test failed.

07

The validation page

The validation page is the report of a tier, written into a copy of the sources of this site: its index.html, the state of every case in results.json, the figures of every case, and history.json, which keeps each comparison of every earlier report so that the page shows how it moved from one commit to the next.

# run the complete tier and write its report into the site
bin/qbmmValidate -complete -site <siteDir>

# report the cases as their last run left them, without running them
bin/qbmmReport -site <siteDir> -tests <log of test/Allrun> [<root> ...]

# write the page again from the results it holds, after a change of its layout
bin/qbmmReport -refresh -site <siteDir>

Nothing is published by these commands: they write the directory, and putting it on the site is a separate step.

08

Adding a test or a case

A unit test

  • A directory under test/ with the source of the test and its Make/files and Make/options, building an application named Test-<Name>.
  • A line in test/Allwmake to build it and a line in test/Allrun to run it, from the directory that holds its dictionaries.
  • The test exits with an error when what it computes is not what it should be.

A case

  • An Allrun that runs each step through runStep (or runStepParallel) of AllrunFunctions, and an Allclean; the initial fields in 0.orig.
  • For a validation case, the reference data under validationData, the figures and the comparisons in validation/validationDict, and a call to plotCase at the end of the Allrun.
  • A baseline, recorded with bin/qbmmRegression record once the result of the case is trusted.
  • A case that takes more than a few minutes goes in the long list of validation/validationTiers; one that has to be run by hand, in the manual list, with how long it takes.
